# Контракт `decide()` и делегирование (M1)

Раздел 5.19 плана. Делегат игрока и ИИ соперника — один и тот же код. Контракт фиксируется в M1, до первой системы, где принимаются решения. Конкретных решающих систем в M1 нет, есть контракт, общий механизм выбора и типы делегирования.

## Контракт

```ts
type DecisionMakerProfile = {
  skill: number;        // 0..1 — насколько близко к лучшему варианту
  consistency: number;  // 0..1 — насколько редки грубые ошибки
  rapport: number;      // 0..1 — рабочее взаимопонимание с игроком
};
type Intent<TGoal extends string> = {
  goal: TGoal;          // например 'qualifying' | 'race' | 'tyre-saving' для сетапа
  risk: number;         // 0..1
  issuedBy: 'player' | 'team-character';
};
type Decide<TContext, TGoal extends string, TChoice> = (
  context: TContext, competence: DecisionMakerProfile, intent: Intent<TGoal>, rng: Rng,
) => Decision<TChoice>;
type Decision<T> = { choice: T; considered: readonly ScoredOption<T>[] };
type ScoredOption<T> = { option: T; score: number; reasons: readonly string[] };
```

Отличие от черновика плана: `decide()` возвращает не голое `TDecision`, а `Decision<T>` — выбор вместе с рассмотренными вариантами и причинами. Правило 1 из 5.19 требует, чтобы обоснования были видны всегда, а отчёты делегатов разворачиваются в обоснование (6.5). Если бы контракт возвращал только выбор, обоснование пришлось бы восстанавливать отдельно.

## Общий механизм: `chooseByScore`

Каждая будущая система предлагает варианты и функцию оценки под указание. Выбор делает общий код:

1. Для варианта считается истинная полезность под `intent`.
2. Решающий видит её с шумом. Разброс шума убывает с `skill`: сильный сотрудник выдаёт 90–97% достижимого (5.19).
3. С вероятностью, растущей при низкой `consistency`, случается грубая ошибка — большой разовый сдвиг оценки. Слабый проигрывает разбросом, а не средним.
4. Выбирается максимум воспринимаемой полезности. `rapport` уменьшает шум по отношению к предпочтениям игрока. В M1 это поле есть, эффект заработает вместе с первой системой, у которой есть история решений игрока.

Контекст, которого нет в указании, делегат не знает. Он оптимизирует под цель по умолчанию, и именно в этом его проигрыш игроку. ИИ-команда передаёт в `intent` цель из своего характера, а в `competence` — профиль своего сотрудника. Отдельного пути для ИИ нет.

## Делегирование

- **Области** — 11 из таблицы 5.19: `setup`, `practice-programmes`, `race-strategy`, `race-radio`, `development`, `hiring`, `social`, `sponsorship`, `scouting`, `driver-training`, `tyre-allocation`. Пресс-конференции (особый случай «делегировать можно, но не бесплатно») появятся в M9.
- **Режимы** — `manual`, `directed`, `delegated`.
- **Кто ведёт область** — связка «область → роль сотрудника» задаётся данными. Область доступна для делегирования, только если в команде есть человек на этой роли. В режиме B штат неполный, поэтому часть областей принудительно ручная.
- **Пресеты** при старте: «Полный контроль», «Руководитель», «Только гонки» (5.19).
- **Профиль из сотрудника**: `skill` и `consistency` берутся из атрибутов сотрудника (1..100 → 0..1), `rapport` поначалу 0.

## Константы (`src/data/balance/decide.json`)

Разброс шума при навыке 0 и 1, вероятность грубой ошибки при `consistency` 0 и 1, размер ошибки, сила эффекта `rapport`.

## Тесты

- Сильный профиль выбирает лучший вариант заметно чаще слабого.
- Разброс качества выбора у слабого больше.
- Одинаковые вход и поток дают одинаковый выбор.
- В `considered` есть все варианты.
- Для игрока и для ИИ вызывается одна и та же функция — это проверяется самим устройством кода.
